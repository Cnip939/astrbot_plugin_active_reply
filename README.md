# astrbot-plugin-active-Reply

使用大模型判断的主动回复插件

主版本，会完全更改上下文结构，可能有未知问题

## 配置说明

| 配置项 | 作用 |
| --- | --- |
| `active_reply_enabled` | 主动回复模式总开关。开启＝由本插件判定 REPLY/SKIP 并自行接管上下文；关闭＝只做图片注入，回复时机与上下文交给其他负责拼装的插件。 |
| `group_blacklist` | 群聊黑名单。写进这里的群不再进行主动回复判定（详见下节）。 |
| `persist_history` | 聊天记忆持久化，默认开启；关闭＝重启即清空（调试用）。详见「聊天记忆与持久化」。 |
| `persist_images` | 持久化时是否保留图片，默认开启；关闭则写盘时降级为 `[图片]`。 |
| `sleep_time_adaptive` | 等待时长自适应，默认开启；关闭＝固定等 `sleep_time`。详见「等待时间（自适应）」。 |
| `log_prompt` | 把每次判定的完整提示词以 INFO 级别打进日志，默认关闭。详见「日志」。 |

### 群聊黑名单 `group_blacklist`

写进黑名单的群：**不再做 REPLY/SKIP 主动回复判定，也不会主动开口**；但**被@或引用机器人时
仍由本插件强制回复**（被@属于被动应答，不算主动回复），走的是和开启主动回复时完全一样的
强制回复路径与群聊流水账上下文。其余消息的群聊记录（记忆）与图片注入照常，回复时机交回
平台与其他插件（例如 group_chat_plus）。

写法：

- 直接填群号，一行一个；WebUI 里可以点「批量导入」一次粘贴多行：

  ```
  123456789
  987654321
  ```

- 也接受完整消息来源，`aiocqhttp:GroupMessage:123456789` 与只写 `123456789` 等价。
- 一行里用逗号、分号或空格分隔多个群号同样有效。
- 以 `#` 开头的行或条目按注释忽略。
- 留空（默认）＝不屏蔽任何群。

私聊不参与黑名单比对（避免用户 QQ 号与群号撞号被误伤）。

> 在 WebUI 保存插件配置后，AstrBot 会自动热重载本插件，黑名单立即生效。

## 等待时间（自适应）

`sleep_time` 是"收集窗口"的基准长度：一条消息触发后等这么久，把这段时间里群友的后续消息
并进同一轮，再统一判定要不要回复。

开启 `sleep_time_adaptive`（默认开启）后，实际等待时长跟着**群里此刻有多热**浮动：

- **刚有人说过话**（群里正热）→ 多等一会，最多 **2 × `sleep_time`**
- **冷场很久后突然来一句** → 快速判定，最少 **1 秒**

曲线是 `y = 1 + (2S-1)·T/(x+T)`（一条直角双曲线，`T = 2(S-1)/S`），其中 `x` = 距上一条
**群友**消息的秒数（机器人自己发的不算，否则它刚回完一句，下一条一定被判成"热聊"）：

| 静默 x | → 0 | 2 秒 | 越大 |
| --- | --- | --- | --- |
| 等待 y | 2S（上限） | S | 趋近 1 秒 |

以 `sleep_time = 12` 为例：

| 静默 x | 0.5s | 2s | 5s | 12s | 60s | 2min | 4min |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 等待 y | 19.1s | 12.0s | 7.2s | 4.0s | 1.7s | 1.3s | 1.2s |

规则细节：

- **被 @ 机器人时强制减半**：等待时间直接取 `sleep_time / 2`（最低 1 秒），不看密度曲线。
  这条**不受 `sleep_time_adaptive` 开关影响** —— 被点名叫到就该快回。
  注意只有 **@** 才算；单纯**引用**机器人的消息虽然同样会强制回复，但等待时间照常走曲线。
- **等待期间只要还在来消息就顺延**：每来一条就把截止时刻往后推（只推不缩 —— 新消息不该让 bot
  更早开口），但**整轮总时长封顶 2 × `sleep_time`**，热闹的群不会一直续命、永远等不到头。
- **重启后视为冷启动**：没有"上一条消息"的记录，第一次按基准值 `sleep_time` 处理。
  这份记录只存在内存、不持久化。
- 命令屏蔽符挡掉的消息、空消息不计入"上一条消息"。
- `sleep_time` 设成 `0` 时**保持旧行为**（不等待、直接判定）；设成 `0 < S < 1` 时
  `[1, 2S]` 是空区间，固定等 1 秒。
- 关闭 `sleep_time_adaptive` 就退回固定等待 `sleep_time`（被 @ 时仍减半）。
- 日志里会打一行 `[轨迹] 本轮等待约 7.2s（静默 5.0s，基准 12.0s）`，被 @ 时显示
  `（被@，强制减半，基准 12.0s）`，方便核对。

## 聊天记忆与持久化

每个会话都有一份「群聊流水账」：群友说的话、机器人自己说过的话、时间戳，构成主动回复判定
和模型上下文的基础。条数上限由 `max_history` 控制，超出的从头部丢弃（**落盘文件里存的也是
截断之后的内容**，和内存始终一致）。

### 重启不丢历史

开启 `persist_history`（默认开启）后，流水账写进：

```
data/plugin_data/astrbot_plugin_active_reply/history/<会话键>.json
```

- **写入是"准实时"**：消息先写内存，后台任务每 1 秒把变动过的会话批量落盘；插件重载或
  AstrBot 正常关闭时会再强制写一次，所以正常重启**一条都不会丢**。只有强杀进程
  （`kill -9`）才会丢掉最后不到 1 秒的内容。
- **文件是原子写**：先写 `.tmp` 再替换，断电不会留下半个文件。
- **读取失败即重建**：某个文件损坏到读不出来时，日志里会打一条带完整堆栈的 ERROR，
  然后**直接丢弃该文件、用一份全新的空记录覆盖它**，这个会话从头开始记；插件本身不会被拖垮。
- **等待中的那一轮不恢复**：`sleep_time` 收集窗口里还没判定的那几条消息属于"进行中的一轮"，
  重启后直接丢弃，不会出现某个会话卡在"永远在收集、永远不回话"的状态。
- **图片**：`persist_images` 控制图片 base64 是否跟着写盘。开启（默认）则重启后模型仍能看到
  最近 `picture_quantity` 张图；关闭则写盘时降级成 `[图片]`，文件体积能小几个数量级。
- 关闭 `persist_history` 就回到旧行为：**重启即清空**，适合调试。

会话键形如 `group_123456789`（群聊）或 `private_10086`（私聊），所以同一个 QQ 号既私聊、
又待在一个同号的群里时，两边**不会**共用记忆。

### 手动清空

在会话里发送（需要 AstrBot 管理员权限，命令前缀与全局唤醒前缀一致，默认 `/`）：

```
/clear_history
```

别名：`/清空历史`、`/清空记忆`。会同时清掉内存里的流水账和对应的落盘文件。

**清空不会留下污染：**

- 命令本身以唤醒前缀开头，会被命令屏蔽符挡在流水账之外，不会记进记忆。
- 机器人的那句「已清空」确认回复也会被跳过，不会写回刚清空的历史。
- **如果清空时正好有一轮消息在 `sleep_time` 收集窗口里**，那一轮会被标记作废：它到点后
  不判定、不回复、不记账。否则几秒后它收尾时会把自己写回刚清空的历史，等于白清。

也可以直接删 `data/plugin_data/astrbot_plugin_active_reply/history/` 下的文件，插件没在跑的时候删最保险。

## 消息分段

把一条长回复按分隔符（默认换行）拆成多条发出，群聊和私聊各有一套开关与上限。

| 配置项 | 默认值 | 作用 |
| --- | --- | --- |
| `segment_enable_group` / `segment_enable_private` | `true` / `true` | 群聊 / 私聊分段开关 |
| `segment_regex` | `[\n]+` | 分段分隔符正则（匹配到的部分当分隔符） |
| `segment_max_group` / `segment_max_private` | `3` / `3` | 群聊 / 私聊最大分段数，`0`＝不限制 |
| `segment_delay` | `0.5` | 分段之间的发送间隔（秒），`0`＝不等待 |
| `segment_blacklist` | `[]` | 命中这些会话（群号或 QQ 号）时**不分段** |

规则：

- **超过上限就不再切**：只切 `上限-1` 刀，剩下的内容全部并进最后一条，原来的换行原样保留。
- **引用优先于上限**：带引用的句子不受分段上限约束（见下一节）。
- 非文本组件（图片、@）不参与切分，跟着它所在的那一条走。
- 分段关闭或命中黑名单时整条一次发出；此时如果模型写了多个引用，**只保留第一个**，其余标记删掉。

## 模型自主引用

开启后，**「当前消息」里的每句话前面会带上编号**（历史记录不带编号、也不参与引用），模型可以用
`[replyN]` 引用其中某一条：

```
（prompt 里模型看到的）
当前消息：
1. 老大[3688403726]:我饿了
2. 小明[10086]:吃什么呢

（模型可以这样输出）
[reply1]那你吃点东西呀
[reply2]我也不知道吃啥
```

- **编号就是本轮消息的顺序**（从 1 开始）。一轮的消息在收集窗口（`sleep_time`）结束时冻结，
  之后来的消息属于下一轮、编号重新从 1 开始，所以编号和消息的对应关系**永远不会被改写**。
- **一条消息只能带一个引用**（QQ 的限制），所以每个带引用的句子都会单独成为一条消息。
- 编号无效（越界）时：只把标记删掉、文字保留，不强行分段。
- 标记大小写与冒号都容忍：`[Reply3]`、`[reply:3]`、`[ reply 3 ]` 等价。
- 历史记录里**没有编号**、格式不变，模型记忆不受影响。
- 只在**主动回复模式**（`active_reply_enabled` 开启）下生效。

| 配置项 | 默认值 | 作用 |
| --- | --- | --- |
| `quote_enable` | `true` | 自主引用开关 |

已知限制：

- **只能引用"当前这一轮"里的消息**（也就是触发这次回复的那几条，通常 1～3 条）。
  隔了几轮、已经进历史的旧消息引用不到——因为编号只存在于当前这一轮。
- **引用不了机器人自己的消息**。框架不返回自己发出消息的 message_id（`send_message` 是 `-> None`），
  所以编号只覆盖群友发来的消息。
- 只在 aiocqhttp / NapCat 上可靠（`Reply` 是 OneBot V11 的标准消息段）。
- **流式输出下不生效**：正文在生成时就已经发出去，发送前钩子拿不到完整文本。

### 分段与引用怎么配合

以 `segment_max_group = 2` 为例（这里的 `[reply1]`～`[reply5]` 对应「当前消息」里的第 1～5 条，
也就是这一轮收集到 5 条消息的情形）：

```
原始输出：[reply1]hi ⏎[reply2]你好呀 ⏎[reply3]今天怎么样 ⏎[reply4]确实饿了[reply5]是啊吃什么⏎那我不知道了

先分段（上限 2，只切 1 刀）：
  段1 = [reply1]hi
  段2 = [reply2]你好呀⏎[reply3]今天怎么样⏎[reply4]确实饿了[reply5]是啊吃什么⏎那我不知道了

再按引用强制分条（引用不受上限约束，一条消息也放不下两个引用）：
  ① 引用1 + hi
  ② 引用2 + 你好呀
  ③ 引用3 + 今天怎么样
  ④ 引用4 + 确实饿了                 ← 和第 5 个挤在同一行，仍然强行拆开
  ⑤ 引用5 + 是啊吃什么⏎那我不知道了    ← 尾部没有引用，当普通换行跟着最后一条
```

## 日志

插件默认只在 INFO 级别留下少量关键行，其余细节全部走 DEBUG，避免刷屏。

**常开的 INFO：**

| 日志 | 时机 |
| --- | --- |
| `[轨迹] 判定结果: REPLY/SKIP, 理由: ...` | 每次判定结束。这是"群里为什么不回"最直接的答案 |
| `[轨迹] 本轮等待约 X s（静默 Y s，基准 Z s）` | 每轮开始，用来核对自适应曲线 |
| `[历史持久化] 已恢复 N 个会话的历史，目录 ...` | 插件加载时一次 |
| `[清空历史] 已清空 X 的聊天记忆` | 手动执行 `/clear_history` 时 |

**需要开关的：**

| 配置 | 默认 | 作用 |
| --- | --- | --- |
| `log_prompt` | `false` | 开启后，每次判定用的**完整提示词**（含历史记录、当前消息、性格描述等）会以 INFO 打进日志。提示词通常几十行、很占地方，**调提示词时再打开** |

**降级为 DEBUG 的**（要看的话把日志级别调到 debug）：触发消息内容、图片下载/读取、命中黑名单、
分段条数、发起 LLM 请求、注入图片数、强制回复的原因等。

## 分段/引用与"记忆"的关系

- 分段发送时本插件自己发（不再走框架的发送阶段），因此**自己把 bot 说过的话记进群聊流水账**，
  并按约定**合成一行**；没抓到文字的（比如只发了图）不记，避免流水账里出现空行。
- 不分段（只发一条）时仍然交给框架发送，"发送后钩子"照常触发，不影响其他插件。

## 工具调用（function calling）注意事项

**这个钩子跑在 agent 的工具循环里面，不是只在最终回答时跑一次。**
框架每 yield 一次中间结果，都会重跑一遍"结果装饰"阶段，所以 `on_decorating_result` 会被反复调用。

- 工具调用那一轮的助手消息只有 `tool_calls`、正文是空字符串，框架会把它包装成 `[Plain("")]`
  —— 消息链**非空**（所以框架自己的空消息检查拦不住），但一个字都没有。
- 对这类结果，插件只调用 `event.clear_result()` 把这条空消息丢掉，**绝不能 `stop_event()`**：
  事件一被停止，调度器会立刻中断整个 agent 生成器，工具循环被当成"用户中止"提前结束，
  后面那次真正带正文的回复就永远不会发生 —— 现象是「模型一用工具就什么都不回，而且不报错」。
- 同理，分段发送分支在各段都发完之后也只清空结果、不停事件（`clear_result()` 已足够让框架不再
  重复发送原始消息）。

排查时把日志级别调到 debug，会看到：

```
[分段/引用] 本轮结果没有可发送内容（多为工具调用中间轮），跳过不发。原始 chain=[('Plain', "''")]
```

这条是**正常的**，说明插件正确跳过了一个工具调用中间轮并让 agent 继续跑。
